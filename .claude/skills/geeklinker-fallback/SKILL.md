# GeekLinker - аварийный AI-контур

Этот skill - третий, независимый от Gemini API способ проверить источники
GeekLinker на новые статьи. Он не заменяет основной скрипт (GCP) и Make, а
подстраховывает их: реально нужен только тогда, когда они оба не справились
(например, во время сбоя самой модели Gemini, как это уже было 2026-09-28
одновременно на Englishdom ru/ua и Научпоп).

Рабочая директория для всех команд: `geeklinker_bot/` (там лежат `sa-key.json`,
`.env` и все переиспользуемые модули). Перед первой командой в сессии:

```
cd geeklinker_bot
```

Инструменты этого skill - `helpers.py` в этой же папке, CLI поверх
существующих модулей проекта (`config.py`, `sheets.py`, `feeds.py`,
`notify.py`, `rss_discovery.py`). Он же сам проверяет robots.txt на каждом
шаге, где это уместно - отдельно это делать не нужно.

**Важно:** вывод всех команд `helpers.py` всегда перенаправляй в файл и читай
файл через Read, а не читай stdout напрямую из Bash - в этом окружении
возможны проблемы с кодировкой кириллицы при прямом выводе в консоль.

## Шаг 1. Получить список источников

```
python .claude/skills/geeklinker-fallback/helpers.py list_sources > /tmp/sources.json
```

(используй свою scratchpad-директорию вместо `/tmp`). Прочитай файл. Каждый
источник - `{site_name, url, source_type, target_sheet, engine}`. Источники
с `source_type == "!blocked"` в список уже не попадают (отфильтрованы).
`engine` здесь не важен - контур проверяет источники независимо от того, кто
их обычно обрабатывает.

## Шаг 2. Для каждого источника получить статьи

**Если `source_type == "rss"`:**

```
python .claude/skills/geeklinker-fallback/helpers.py fetch_rss "<url>" > /tmp/rss_<n>.json
```

Это чистый парсинг RSS (feedparser), Gemini не участвует и тут не нужен -
просто прочитай результат: список `{link, title, pub_date}` уже готов.

**Если `source_type == "scrape"`:**

```
python .claude/skills/geeklinker-fallback/helpers.py fetch_scrape_html "<url>" /tmp/page_<n>.html
```

Прочитай сохранённый HTML через Read (или Grep, если файл большой - сначала
поищи повторяющийся паттерн карточки статьи, как в реальных примерах ниже, и
прочитай только релевantные куски). Определи список статей на странице
**сам, своим чтением** - именно это заменяет Gemini. Для каждой статьи нужны:
точная ссылка (полный url), заголовок, дата публикации.

Подсказки по структуре (могут отличаться на других сайтах - смотри по факту):
- Englishdom: `<div class="blog-item ...">...data-date="YYYY-MM-DD HH:MM:SS"...
  <a href="/blog/<slug>/" title="Заголовок">` (для `/ua/blog/` - href с
  префиксом `/ua/blog/`).
- imena.ua: `<article id="post-...">...<h2 class="entry-title"><a
  href="URL">Заголовок</a></h2>...<time datetime="YYYY-MM-DD HH:MM:SS">`.

Если структура источника незнакома - просто прочитай HTML вдумчиво и найди
список статей визуально (заголовки, ссылки, даты рядом) так же, как делал бы
человек, просматривающий страницу.

Дату приводи к формату `ДД.ММ.ГГГГ` (как everywhere в проекте).

**Прочие типы** (тип не указан/не распознан) - пропускай: это резервный
контур, автоопределение типа - забота основного скрипта.

## Шаг 3. Проверить, что реально ново

Собери все url со всех источников в один JSON-список и выполни:

```
python .claude/skills/geeklinker-fallback/helpers.py check_dedup /tmp/all_urls.json > /tmp/new_urls.json
```

Это вернёт только те url, которых ещё нет в `_Dedup` - то есть настоящие
кандидаты в новые статьи. Если список пуст - на этом источнике всё уже
обработано, отчитайся и переходи к следующему.

## Шаг 4. Добавить новые статьи

Для каждой по-настоящему новой статьи (только из списка `new_urls.json`,
сопоставленного обратно с её title/pub_date/site_name/target_sheet):

```
python .claude/skills/geeklinker-fallback/helpers.py add_article "<site_name>" "<target_sheet>" "<url>" "<title>" "<ДД.ММ.ГГГГ>"
```

Эта команда сама: пишет в `_Dedup`, добавляет в целевой лист (через формулу
`HYPERLINK`, как основной скрипт), сортирует целевой лист по дате,
отправляет уведомление в Telegram. Если статья внезапно уже оказалась в
`_Dedup` к этому моменту (гонка/повтор) - команда тихо пропустит её и
сообщит об этом, ничего не сломав.

**Этот skill намеренно НЕ пишет в лист "Логи"** - та механика завязана на
блокировку параллельных прогонов основного скрипта (`acquire_run_lock`/
`finish_run_log` в `main.py`), и вмешиваться в неё отсюда не нужно. Сигнал о
работе этого контура - сами уведомления в Telegram по найденным статьям, плюс
итоговое сообщение пользователю в конце.

## Шаг 5. Итог

В конце — коротко перечисли пользователю: сколько источников проверено,
сколько статей было реально новых и добавлено (с названиями), и были ли
источники, которые не удалось проверить (например, HTTP-ошибка или
robots.txt запретил доступ) - это не ошибка исполнения skill, просто
зафиксируй как факт.
